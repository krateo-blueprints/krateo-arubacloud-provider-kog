# Aruba Cloud KOG — resource coverage matrix

Generated by `scripts/gen_samples_and_coverage.py` from the RestDefinitions under `restdefinitions/`. No proxy/plugin is used for any resource.

**36 manageable resources** across 10 providers.

## Support tiers

A tier states what has actually been *executed* against the live Aruba API, not how correct a RestDefinition looks. Every serious defect found in this repository was invisible to review and surfaced only on a cluster, so a resource is only promoted when there is evidence to link.

### What does not count as evidence

Each of these was recorded in this repository as a result, and each is a true statement that answers a question nobody asked.

**An absence on a path that was never walked.** *"No 401, no 403 and no missing-token error across ~20k lines of controller log"* was reported as proof that delegation worked. The controller had never called the delegate at all — verification failed before dispatch — so the absence of errors was an absence of traffic. Before reporting that something did not fail, establish that it ran.

**A correct observation on a path you did not test.** Stronger, and more expensive, than the absence above — because here the measurement is *sound*. `X-Snowplow-Stage-Outcomes: []` was measured on a cluster with no cloud server, checked against the Snowplow maintainers' own written prediction, and recorded as confirmation. It was correct. It was also produced by an iterator that could never send anything, so the identical header meant "nothing to do" in the case tested and "this lifecycle is inert" in the case that mattered — and the second case silently orphaned a billable server. No amount of care about the *measurement* would have caught it: the verification was valid and the inference from it was not. Agreement with a prediction is not evidence that the thing under test works, unless the test could have disagreed.

**A check that cannot fail.** A `|| die` guard is read as proof the failure mode was considered, and it was — but the command before it succeeded unconditionally, so the guard was unreachable while the thing it protected was being overwritten. The misleading part was the safety net's *existence*: a reviewer's eye stops at the `||` and reads reassurance. The question that finds these is not "is this check correct" but "what can this check structurally not report".

**A one-shot sample of a varying quantity.** Host CPU was reported at 1196% of 800% and used to justify deleting a cluster; a later single sample read 125%. Both were single instants. Disk at *0 bytes available* was the trustworthy reading from the same afternoon, because it is a state rather than a sample. Distinguish the two before acting on either.

**A conclusion from the cheapest sample.** `CSO1I1` was refused *"not available for trial"* and read as "this account cannot create cloud servers". `CSO1A2` is accepted. The refusal was per-flavor, and the flavor that had been tried was the smallest one — chosen to minimise cost. **Cheapest-first is right for spending and wrong for sampling**: when testing whether a capability exists, vary the thing under test, not the thing being economised on.

**An empty reading rendered as a confident number.** `$(cmd)` that fails yields an empty string, and every aggregator turns an empty string into a plausible value: `awk '{s+=$1} END {print s}'` over no input prints `0`. A peer measuring host CPU wrapped each sample in `timeout 60 docker stats` — **`timeout` does not exist on macOS** — so every invocation failed, the stream was empty, and the instrument reported `0%` three times in a cleanly formatted line. The same summation here would have done the same thing, and the same `timeout` was missing in this repository's own commands earlier the same day. This is not a fourth axis but a **precondition on all of them: assert the reading is non-empty before interpreting it.** `grep -c .` on the raw output before any arithmetic is enough, and the count belongs in the reported line so a reader can see it was taken.

**A measurement taken before the thing under test was running.** An image swap was read as "the fix does not work" while the controller was still on the old image: oasgen re-renders each generated controller on its own reconcile schedule, so a cluster-level check can report a candidate the controller under test has not yet picked up. Verify the artefact is running, per controller, before reading anything.

**A conclusion that explains the symptom without explaining the other evidence.** The costliest one here, at roughly four hours. Two findings were held at once: *RDC never called snowplow at all*, and *the delete iterator yields `[]` because it reads `$s.id` on a shape whose identifier is at `metadata.id`*. Both were measured, both were recorded, and they cannot both be the cause — if the RESTAction never runs, its jq never evaluates. The second explained the stranded server so neatly that the contradiction was never examined, and it was reported upstream to three sessions as the root cause. Phrasing owed to the oasgen-provider session: a correction deserves the same scrutiny as the claim it replaces, and it arrives with the confidence of having just learned something, which is when it is least examined.

**A measurement of the wrong process.** “Zero DELETE requests, beyond doubt” was true and meaningless: on a delegated path snowplow issues the request, not RDC, so RDC’s verbose dump could never have shown one. The same dump also does not instrument the snowplow client, so “zero calls to /call” proved nothing either. Before trusting an absence, establish that the thing you are watching is the thing that would act.

**An error message read as the symptom rather than the cause.** Aruba answered a drift PUT with `400 {"fieldName":"Flavor","errorMessage":"Please specify flavor."}`, reproduced on three separate servers and recorded as a vendor defect in the update verb. It is CREATE-body validation: the OAS declares `DELETE, GET, PATCH` for that path and no PUT — the one item path in the whole vendored set that does — so the PUT reached a create-like handler. The message named the cause. Three servers of consistent evidence confirmed a reading of it that was never checked against the schema.

**A number that lands near a plausible ratio.** A chart install took 13s at 316 MB and 5s at 32 MB on a GitHub runner — a 2.6x ratio, close to the 2.8x that the *uncompressed* sizes give and nowhere near the 10x the wire bytes give. Both measurements were mostly fixed overhead on a runner sitting next to the registry, so neither tests anything; but the ratio agreed with a figure well enough to be quotable. A number that agrees is waved through where a number that disagrees is investigated.

**Two readings of a changing quantity, compared as though simultaneous.** A cross-check reported `INSTRUMENT DISAGREEMENT … one of the two is wrong` on its first real run. Neither was wrong: the per-resource check ran during that resource’s teardown and the residue listing ran nine minutes later, after the delete had succeeded in between. The check now re-reads the item before claiming a contradiction. This is the one-shot-sample error wearing a different hat — two samples of a state that moved.

**A capability missing from your command line, reported as missing from the tool.** An hour was spent diagnosing a delegated mutation that logs its decisive line at DEBUG, and the conclusion reported upstream was that generated controllers have no verbosity control. `scripts/pin_verify.sh` has carried `RDC_DEBUG` and `--set-string rdc.env.REST_CONTROLLER_DEBUG=true` throughout, with a comment explaining the schema trap that makes `--set` fail — written by the same person who then reported the lever absent. Check your own tooling before reporting a gap in someone else’s.

**A generated schema read off a cluster on an old pin.** Three times in one day, `kind-aruba-110` gave a confident wrong answer about generated CRDs — most consequentially `spec.metadata` appearing to expose only `['name']`, which nearly settled that a CR could not declare tags at all. On the current pin it is `['location','name','tags']`. That cluster exists only to hold a credential; schema questions get read off a cluster on the pin under test.

### The stack the evidence was measured on

A tier is a claim about a stack, so the stack belongs next to it. The live runs behind these tiers were executed on the `kind-aruba-110` cluster, which is **not** the stack the install docs describe:

| | live evidence cluster | CI / install docs |
|---|---|---|
| chart | `oasgen-provider-0.24.0` | `0.27.1` |
| provider image | `local/oasgen-provider:108-live` | released `0.27.1` |
| RDC image | `local/rest-dynamic-controller:110-test` | released `0.27.1` |

The provider image is also **drifted from its own Helm release**: the release's values ask for `110-test`, while the running Deployment is `108-live`, patched in place afterwards. Anyone running `helm upgrade` on that cluster would silently revert the provider under the evidence. Neither local image carries a label recording what it was built from.

oasgen-provider is a monorepo releasing oasgen-provider and rest-dynamic-controller in lockstep, so installing `0.27.1` gets RDC `0.27.1`.

**This gap is now closed** (2026-10-22). `scripts/pin_verify.sh` builds a cluster matching CI exactly — pinned node image, pinned charts, no image overrides — and runs the free `network-security` chain on it. All 34 generated controllers came up on released `ghcr.io/krateo-platformops/rest-dynamic-controller:0.27.1` under `oasgen-provider:0.27.1`, and all four resources went create → observe → **drift corrected** → delete verified 404, residue clean. ESO minted its first token on that stack on the first check, so unattended credential handling holds there too. The behaviour the tiers describe is the behaviour of the released stack, now measured rather than inferred.

What this does and does not put at risk: every provider feature these RestDefinitions rely on is present in the pinned release — `responseTransform`, which is what carries `Kaas`, `Registry` and `Job`, exists in `0.27.1` in both the RestDefinition CRD and the RDC client, and CI's static validation would reject the field otherwise. So no tier here depends on unreleased code. What is *not* yet proven is that the live-API runs reproduce on the released images rather than the local ones. Until one chain is re-run on a cluster built from the pin, treat that as the one gap between these tiers and a user's install.

**FULL DELEGATED LIFECYCLE PROVEN LIVE (2026-10-30)**, after two defects that made every delegated delete a silent no-op. A `CSO1A2` was created, observed, deleted by its own delegated RESTAction, and the finalizer released by the controller **without intervention**: 5/5 deletes verified and attributed, 0 wait-timeouts, 0 unattributed, 0 instrument disagreements, snowplow logging one `calling api name=delete` and no `skipping api call`, and the account clean by id afterwards. GA on the `create → observe → delete` bar.

**Its update is UNTESTED, and the “vendor blocker” claim that stood here is WITHDRAWN.** It said Aruba’s PUT answers 400 for every body shape tried — `Flavor: Please specify flavor.; Product: not found`, reproduced on three separate servers. The reproduction was real and the conclusion was wrong: **the OAS declares `DELETE, GET, PATCH` for `cloudServers/{cloudServerId}` and no PUT**, and this repo’s drift machinery hardcoded PUT at both call sites. Across the whole vendored set, 29 item paths declare PUT and exactly one declares PATCH without it — this one. So the 400 was Aruba rejecting a PUT to a PATCH-only endpoint, reaching a create-like handler, which is why it asked for a `Flavor` and a `Product`: that is CREATE-body validation. The error named the cause and it was read as the symptom, three times.

`scripts/ga_chain.py` now DERIVES the method from the OAS (`update_method()`), so drift uses PATCH where no PUT is declared. CloudServer’s drift has therefore never been exercised with the correct verb and is **unproven rather than blocked** — a materially weaker claim than the one withdrawn, and nothing upstream was filed on the wrong one.

**The two defects were both in this repo’s RESTActions and both were invisible by construction.** Recorded because the shapes generalise to any delegated resource:

1. *A stage `filter` is evaluated on an envelope* — `{extras, <stage name>}` — not on the response body. The filters read `.spec.metadata.name` and `.values`, which is what `path` and `dependsOn.iterator` see (those get the resolver dict). In a filter both are absent, and jq resolves them to null **silently**, so the filter returned a well-formed result that was simply always empty. `self` was null on every call, both iterators yielded `[]`, nothing was sent. snowplow#998.
2. *`$.` is not valid jq* — `$` must be followed by a variable name. Six path templates used `$.spec.projectId`, so jq rejected the whole expression and snowplow logged `skipping api call: path jq expression errored` at DEBUG, invisible at its default `LOG_LEVEL=warn`. Every delegated write stage was disabled, update included. snowplow#1001.

Both are gated in CI now: `verify_restaction_filter_envelope` rejects a filter reading a root key outside `{extras, slice, <stage>}`, and `verify_restaction_jq_compiles` compiles all 20 expressions with real jq. They catch different things — jq compiles a filter reading absent keys perfectly happily, which is exactly why the first bug outlived the second.

**What reported success while nothing happened**, stated because the absence of a signal was the only signal: snowplow answered 200, `X-Snowplow-Stage-Outcomes` was `[]` (it lists only stages that did NOT succeed, so `[]` means all succeeded), and RDC logged `Mutated via RESTAction`. Every layer was correct and the server stayed Active through 23 attempts. Only oasgen#261’s not-addressable guard noticed, by refusing to drop the finalizer — without it this would have orphaned a billable server on **every** delete for as long as the bug persisted. snowplow#989’s per-stage iteration counts would have shown `delete: 0 items` on the first call.

**observe proven live** (2026-10-20): a server was created directly over the API and the CR converged on it, reporting back the same id the POST returned (`6ad732b8`), which exercises the only two verbs it declares — `findby` and `get`. Before this the sample had only ever been applied against an empty collection, which proves nothing. Run it with `scripts/ga_cloudserver_observe.py`.

**Create is NATIVE and wired as of 2026-10-28**, and the long note that used to stand here — that it was unreachable and quarantined under `tests/experimental/` — is obsolete. The create endpoint exists only in `compute-provider_v1.1.json`, so the verb carries a per-verb `oasPath` onto that document, which requires oasgen [#227](https://github.com/krateo-platformops/oasgen-provider/pull/227) (0.34.0); below it the field parses and is silently ignored and the create resolves against the 1.0 document, which has no POST for the path.

**Routing is proven; the create is REFUSED for account reasons.** Aruba answers the POST with field-level validation errors — `FlavorId`, `DataCenter`, `Product` — and not `operation not found: POST`, which is what proves the per-verb `oasPath` reaches the 1.1 endpoint. What it then says is `{"fieldName":"FlavorId","errorMessage":"<uuid> not available for trial"}`, for `CSO1I1`, the smallest of the 40 flavors the catalog returns. The catalog exposes only `{name, cpu, ram}`, so which flavors an account may use is not discoverable before the attempt — [Arubacloud/api#29](https://github.com/Arubacloud/api/issues/29).

**CREATE IS PROVEN LIVE (2026-10-29).** A `CloudServer` was created from a CR with `flavorName: CSO1A2` and went `InCreation -> Active` in **61s**, the first ever created from a CR in this repository. Four of the five resources in its chain also had drift injected and corrected.

**AND THE SAME RUN FOUND THAT THE DELEGATED LIFECYCLE SENT NOTHING AT ALL, WHICH ORPHANED THAT SERVER.** A collection item on this API has exactly `{metadata, properties, status}` — the identifier is at **`metadata.id`** — and every iterator in the delete and update RESTActions tested `$s.id`, which is therefore always null. Each yielded `[]`, so **no request was ever sent**: 12 occurrences covering delete, volume detach, power state, subnets, security groups and data volumes. The entire delegated lifecycle was inert.

A stage iterating zero items **succeeds**, so Snowplow answered `200` with `X-Snowplow-Stage-Outcomes: []` — byte-identical to the header for "nothing to do" — while RDC retried forever with `delete of ga-cs-server did not remove the external resource, which is still present`. The CR wedged on its finalizer and the server billed until it was deleted by hand; a single hand-issued DELETE removed it at once, so the API was never the problem.

**If you created a CloudServer with this provider before 2026-10-29, check your account.** The controller did not delete it, and said nothing.

**This class of bug becomes detectable upstream.** The ambiguity that hid it — a stage iterating zero items being reported identically to a stage with nothing to do — is now [snowplow#989](https://github.com/krateo-platformops/snowplow/issues/989), scheduled for 1.12.62 or later: a separate additive header `X-Snowplow-Stage-Iterations` listing each looping stage with its item count, leaving `X-Snowplow-Stage-Outcomes` unchanged. A `delete: 0 items` would have made this visible on the first run instead of after a stranded server. When it ships, assert on it in any chain that delegates.

Fixed, and verified with jq against the real response shape (`$s.id` -> `[]`; `$s.metadata.id` -> the id). **The fix is not yet proven live** — that needs another real server — which is why this stays at **beta**: `findby`, `get` and now `create` are proven; `update` and `delete` are not.

Drift is **SKIPPED** for a reason the fix also explains: the chain reported `PUT returned 400 for every body shape tried — Flavor: Please specify flavor.; Product: not found`, and the delegated update that should have handled it had all four of its stages inert.

Undeclared constraints the OAS does not state, each found by a refusal: the boot volume must be `bootable: true` **with** an image code (a plain volume never boots); `securityGroups` is **required** (`GenericResource: securityGroup cannot be null`) though the request schema marks nothing required; and `dataCenter` is **not the location** — it is a zone WITHIN one (`ITBG-1`, not `ITBG-Bergamo`), a mapping that exists only at `GET /catalog/locationAndDataCenter`, undocumented on the portal ([Arubacloud/api#26](https://github.com/Arubacloud/api/issues/26)).

**A correction, because this document carried the opposite claim.** It was recorded here that the API returns only the FIRST validation error, which was used to explain why a flavor probe could not work. That is wrong, and it was measured on 2026-10-28: a POST with two deliberately invalid fields returns BOTH — `[{DataCenter, not found on selected location}, {Product, not found}]`. The reason a probe still cannot settle flavor eligibility is different and narrower: the trial check runs only after every reference in the request resolves, so a request deliberately broken elsewhere never reaches it. Reaching it needs an otherwise-valid request, which is a real server.

**Delegation needs FOUR prerequisites, and the chart provides none of them** — `rdc.env.URL_SNOWPLOW`, `rdc.env.URL_AUTHN`, an `audience: authn` projected token mounted at `/var/run/secrets/krateo.io/serviceaccount`, and a `serviceaccount.authn.krateo.io` CR matching the controller's ServiceAccount plus RBAC for its groups. **Proven sufficient for a CALLER, not yet for RDC** — and the distinction is a correction to what this entry said on 2026-10-28. A probe pod using RDC's own mechanism (an `audience: authn` projected token exchanged at `/serviceaccount/login`, then the JWT to `/call`) authenticated and received valid `X-Snowplow-Stage-Outcomes` on snowplow 1.12.57 and 1.12.58. **RDC's own delegated call has never been observed**, because verification fails before dispatch when the id is missing ([oasgen#261](https://github.com/krateo-platformops/oasgen-provider/issues/261)) — so the absence of 401s in the controller log is the absence of errors on a path that was never walked, which is not evidence. Wired in `scripts/pin_verify.sh` under `WITH_SNOWPLOW=1`; filed upstream as [oasgen-provider#262](https://github.com/krateo-platformops/oasgen-provider/issues/262).

**And a create that fails leaves the CR undeletable** — [oasgen-provider#261](https://github.com/krateo-platformops/oasgen-provider/issues/261), fixed in 0.41.0. The `deleteApiRef` path verifies the delete through the observe verb, which needs an id a failed create never produced, so it loops on `verifying deletion via get: missing path parameter: cloudServerId` and holds the finalizer indefinitely; ours sat eight hours. The native delete path handles the same case correctly (`External resource is not addressable, releasing finalizer without calling the API` — verified with a `Vpc` whose create also failed), so the guard exists and is simply not applied on the delegated path. Since Aruba refuses every flavor on a trial account, the FIRST CloudServer a user creates here is one they must then unwedge by hand.

**Requires snowplow >= 1.12.57**, a version floor rather than a preference, for two separate confirmed defects ([snowplow#903](https://github.com/krateo-platformops/snowplow/issues/903) and [#904](https://github.com/krateo-platformops/snowplow/issues/904), both confirmed in code 2026-10-26).

**#904 — a failed stage does not stop a later write, and `/call` still answers 200.** Verified by snowplow against a read -> detach (409) -> delete sequence: the DELETE is sent anyway, the stage error is recorded under `errorKey`, and a filter can hide it completely. For this resource the consequence is specific and our existing safety net does **not** catch it: RDC's delete verification checks the *server* via the observe verb, so a failed volume detach followed by a successful server delete verifies as clean — the server is genuinely gone, the finalizer correctly releases, and the data volumes are orphaned with nothing referencing them. The net catches "the delete did not happen", not "the delete happened and left the wrong things behind".

Note that #904's fix does **not** automatically cover this RESTAction, which is why the floor is stated with the caveat. The fix skips a write step whose `dependsOn` step failed, unless `continueOnError` is set. Here `delete` depends on `server`, not on `detachVolumes` — they are siblings off the same read — and all three stages set `continueOnError: true`, so both exemptions apply. The fix is three lines — `delete.dependsOn` from `server` to `detachVolumes`, and drop `continueOnError` from the delete step **and from `detachVolumes`** — and it is **deliberately not made yet**. The third line was missing from an earlier version of this note, which called it a two-line fix; it was corrected against [snowplow#911](https://github.com/krateo-platformops/snowplow/pull/911), the #904 fix, where leaving `continueOnError` on `detachVolumes` was measured to delete the server after a **failed server read**: detach runs anyway, its iterator over an absent server yields zero items, zero items succeeds, and the delete is waved through (POST 0, DELETE 1). Snowplow pinned down the semantics that cut both ways here: an iterator yielding **zero items has succeeded**, so a server with no data volumes (the common case, and every server the GA chain creates) is still deleted, while a failed detach skips the delete and the response header says so. Below 1.12.57 the delete is sent regardless, so making the change early would add ordering and no protection while reading as though the hole were closed. The exact diff and its reasoning are recorded in `restactions/compute/cloudserver-delete.restaction.yaml`, where whoever raises the floor will find them.

**#903 — background work can send write stages.** Below 1.12.57, Snowplow background work can send a RESTAction's WRITE stages using the endpointRef credential — its "background only reads" guard covers only its own service account. These three RESTActions are not exposed in normal operation: no widget references them, they carry no `userAccessFilter`, so pre-warm and seeding never pick them up, and a resolve that reached the Aruba API is never cached, so the refresher has nothing to replay. The exception is narrow and real: if the endpointRef Secret is absent at the moment of a resolve the result can be cached truncated, and a later refresh — once the Secret exists again — would run the full read → detach → delete sequence against a live server with no user action. **Never let a widget reference these RESTActions.** From 1.12.57 background work sends no write step for any credential, and writes run only on a real request such as the controller's `/call`.

**Delete needs Snowplow.** This RestDefinition routes delete through a RESTAction (`deleteApiRef`), so on a cluster without a Snowplow client the CR cannot be deleted at all — every attempt logs `no snowplow client is configured` and the CR wedges on its finalizer while the remote server is long gone. That is why this is beta and not GA — **billable** — [live-cluster-test](live-cluster-test.md) |

## Not generated (and why)

- **Action-only endpoints** (power on/off, attach/detach, associate/disassociate, download, restore, rename, automaticrenew, resetAdminPassword): not expressible as CRUD verbs — see `oasgen-provider-evolution.md` §C1.
- **List-only endpoints** (`Aruba.Insight/alerts`, `.../metrics`, `Aruba.Audit/events`, job plannings): read-only telemetry, no per-item lifecycle.
- **`compute/CloudServer`** is generated with create/get/findby/delete only; its full lifecycle needs Snowplow delegation — see §C1/C3/C5.
